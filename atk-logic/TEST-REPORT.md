### 5.1 抓到的厂商下发行（地址 4 = 逻辑分析仪）

| # | 帧 | 解码 |
|---|---|---|
| 819 | `0a 87 01` | 裸命令 **唤醒 FPGA** |
| 869 | `0a 11 00 10 06 80 96 98 00 00 a0 86 01 00 00` | 帧命令 0x11：**flags=0x00（非 Buffer）**、阈值 1.6V、hzIndex=6→**20MHz**、深度 **10,000,000**、触发深度 **100,000** |
| 888 | `0a 12 ff ff ff ff ff ff ff ff 00 00` | 帧命令 0x12：8 个通道对全 0xFF（16 通道全使能"任意变化"）+ **尾部 2 字节 0x00 0x00**（共 **10 字节**） |

### 5.2 设备回传（IN）解析

- 厂商按 **16 KB URB** 读（1256 条 16 KB 记录 + 1009 条 512 字节短响应）；
  **每条 16 KB 记录自身是 2048 对齐**的 → 逐记录解交织正确；把 512 字节短响应混进整条流解交织会错位（踩过）。
- 帧统计：`order-1` 9856 帧、`order-6` 441、`order-4` 1（`ff 00 12 03`）、`order-3` 1；
  **无 order-5**（非 Buffer 模式无进度帧 ✓ 与实测一致）。
- 每通道样本字节 1,250,016 × 16 = 10,000,128 采样/通道（≈ 请求的 10M ✓）。

### 5.3 `order-3` 结构（87 字节，本次首解）

```
ff 00 | 10 00 00 00 00 | (c5 09 00 00 00) × 16 | 00
 ↑应答头   ↑首个 5B 字段        ↑每通道 5B 数据量      ↑尾字节
```

- 首个 5B 字段：非 Buffer 模式 = **16**；Buffer 模式 = **触发深度+8**（我们自己的抓取 200000→100008）
  → 它是"设备报的记录/触发位置"，**不是**绝对触发时刻。
- 16 个 5B 值 = 每通道数据量（此处均 2501；对应 1,250,016 字节 → 约每 500 字节计 1）。

### 5.4 结论修正与确认

| 项 | 结论 |
|---|---|
| 触发字节编码 | ✅ 我们按厂商 `triggerStringToByte` 实现的 8 对通道字节**与厂商一致**；厂商额外多 1 个保留字节（共 10 字节），两种都被设备接受 |
| 采集模式 | 厂商默认**非 Buffer**；我们默认 Buffer（两者本机都能出数据） |
| `order-3` | ✅ 结构已解（见 5.3），我们工具里的 `trigger_offset_samples` 就是首个 5B 字段 |
| 触发条件是否构成数据闸门 | **否**（本机固件）：PWM0 **停掉**（真无跳变）+ 非 Buffer + 等待触发，仍回满请求深度（重复 2 次一致）；厂商同样用"等待触发"也没被卡住 |
| RLE | **已解**（解压器在厂商 `pv/thread/thread_work.cpp:172-182`，见 §9 真机证据） |

## 7. 协议解码宿主（208 个 sigrok PD，`srdhost.py`）

厂商上位机的解码器 = sigrok 的 Python PD（框架在 C 侧）。本包用纯 Python 复刻宿主，208 个 PD 直接可用。

**实现的 API 面**（按本地 208 个 PD 的实际用法统计出来的）：

| 项 | 语义 |
|---|---|
| `self.wait(cond)` | `cond=None` 前进一格；`{}` **取当前采样点**（SPI 用它抓初值）；`{pin: spec}` AND；**列表 = OR**，命中项由 `self.matched[i]` 标记 |
| spec | `'l'/'h'` 电平、`'r'/'f'/'e'` 边沿、`{'skip': N}` 超时（**按当前位置起算**，可与边沿组 OR） |
| `self.put(ss, es, out, data)` | `out` = `register()` 返回的下标；ANN 数据 `[类, [文本…]]`，BINARY `(类, bytes)` |
| `self.register(type)` | 返回该实例的输出下标；`OUTPUT_ANN/PYTHON/BINARY/LOGIC/META` |
| 采样率 | **老 API `pd.metadata('samplerate', 值)`**（不是 options；别把 `metadata` 覆盖成 dict） |
| `self.channels` | 通道id → **内部序号**（PD 里 `wait({0:…})` 的 0 就是它，不是硬件通道号） |
| 栈式 | 上层 PD 的 `decode(ss, es, data)` 由宿主**逐包**喂下层 `OUTPUT_PYTHON`；链路按 `inputs` 元数据推导 |

**性能**：匹配点用"涉及引脚的段边界归并 + 二分"跳着找（不逐采样扫描）→ 约 1400 万采样/秒。

**踩过的坑**（都进了 `test_srdhost.py`）：
1. 多引脚 AND 条件不能只从一个引脚的段起点取候选 —— I²C 的 `{SCL:'h', SDA:'f'}`（SCL 整段高电平期间 SDA 才下降）会永远命不中。要归并**所有**涉及引脚的段边界。
2. `wait()` 必须严格前进（否则 PD 原地死循环）；但 `{}` 例外。
3. `skip` 目标越过数据末尾 = **流结束**（抛 StopIteration 让 PD 收尾），否则 `pins` 返回 None，PD 内部 `'%d' % None` 崩。
4. PD 允许注解/二进制**类名是字符串**（如 MIPI DSI 的 `'DATA'`），要按声明表映射成下标，别 `int()`。
5. 叶子 PD 一个通道都没绑 → 应报可读错误（列出需要的通道 id），别静默返回空。
6. 官方存档含触发前长空闲：窗口要**从首个跳变前**开始，慢协议（DHT11 一帧 >120ms）解不到时自动放大窗口重试。

**回传帧 order 之外的坑** 与协议细节见 §4；解码结果（11 个官方样例的关键文本）见 README 表格。

## 9. RLE 压缩（flags bit6）——从"不支持"到真机闭环（2026-09-11）

**起因**：上一轮结论是"厂商上位机源码里没有 RLE 解码器 → 不实现"。
这次把厂商源码整个 shallow clone 下来**全目录 grep**（不再只看 `pv/usb`、`pv/static`），
在 `pv/thread/thread_work.cpp:107-182` 找到解压器：

```cpp
const static qint32 rleSize=512*1024;
quint8* rleBuffer=new quint8[rleSize];//rle解压数据
...
if(isRLE){
    qint32 current=0;
    for (qint32 i = 2; i < analysisData.ullLen; i+=2){
        memset(rleBuffer+current, analysisData.pData[i+1], (quint8)analysisData.pData[i]);
        current += (quint8)analysisData.pData[i];
    }
}
```

标志位同处可查（`pv/controller/session_controller.cpp:231-235`）：`if(isBuffer) b+=128; if(isRLE) b+=64;`。

**教训**：`grep -rli rle pv/` 这种"先看关键目录"的搜法会漏；表现层/线程层的解码逻辑要全树搜
（`--include="*.cpp" --include="*.h"` 全目录），命中后再精读。

**实现**：`atkproto.decode_rle/encode_rle` + `FrameStream(rle=True)` 透明展开 + 参数命令 flags bit6；
MCP 工具加 `rle=False` 参数（capture / capture_multi / save_capture / decode_uart / bus_decode）。

**回归**：
- `test_offline.py` 新增 RLE 组（往返 6 组长度 / 300 长游程拆对 / 奇数尾字节忽略 / count=0 / flags 三种组合 /
  FrameStream 透明展开 / 非 RLE 路径不受影响）→ 套件 51 → **68 项**。
- `test_mcp.py` 新增 RLE 段（走 stdio：回压缩信息 + 压缩率 >50% + 展开后 1000Hz/50%）→ **23 项**。
- 真机 `tools/verify_rle.py` **13 项全过**（表见 PROTOCOL-NOTES §4.5）：

```
✓ 设备确实回了 RLE 对（rle_pairs>0）  pairs=1616
✓ 线上字节 << 展开字节（真压缩）  线上 3232 / 展开 50001（省 93.5%）
✓ 展开后字节数 == depth/8  50000
✓ 混合(跳变)字节数 == 2×周期数  800 个（应 800）
✓ 跳变字节间距 ∈ {62,63}（两个间距 = 一个周期 125 字节 = 1000 采样）  [62, 63]
✓ 每个混合字节内部恰好 1 个跳变（= 每个边沿只落在一个字节里）  检查 800 个
✓ RLE 展开后频率 = 1000Hz  1000.0     ✓ RLE 展开后占空比 = 50%  50.0
✓ 对照：纯电平字节数一致（±2）  压缩 49200 vs 原样 49200
✓ 静态信号：全 0 / 压缩率 > 99%（832 字节）/ 仍回满 depth
```

**踩到的坑（测试脚本自身，值得记）**：
1. 把 `bytes*8`（字节串重复 8 次）当成"位展开"喂给统计 → 频率假报 16 kHz。位展开要用 `P.samples_of()`。
2. 误把"跳变字节"当噪声：1kHz@1MHz 的边沿落在字节中间，一个周期 = 62+1+61+1 = 125 字节，
   那些"长度 1 的游程"是**正常结构**（且每字节内部恰好 1 个跳变）——这类结构判据比"游程长度均一"更可靠。
3. `acquire()` 里会先 `wake()`；PWM0 必须在采集前就启动好，别指望"采集中途再开 PWM"。（本次实测不影响结论）

**RLE 真正的价值：深窗口/高采样率时省带宽与时间**（同一路 PWM0 1kHz，四组对照，`samples_of` 后统计全部一致）：

| 采样率 | 深度 | 窗口 | 不压缩线上字节 | 不压缩耗时 | RLE 线上字节 | 压缩率 | RLE 耗时 |
|---|---|---|---|---|---|---|---|
| 200 MHz | 8,000,000 | 40 ms | 15,977,888 | 3.48 s | **99,632** | **99.2%** | **0.10 s** |
| 1 MHz | 2,000,000 | 2000 ms | 3,999,136 | 2.87 s | 16,032 | 93.6% | 2.01 s |

两种模式下频率 1000.0 Hz、占空比 50.0% 完全一致 → 展开正确；200 MHz 下 RLE 把 15.9 MB 的传输压到 100 KB，
采集耗时降到 1/35（USB 带宽就是瓶颈）。**要开大窗口抓长事件时优先 `rle=True`。**

# 第二部分：UART 串口数据采集解码测试（2026-07-31，历史）

## 一、测试目的
验证「PC 串口发送 UART → 逻辑分析仪采集 → 解码还原」链路，含中文/英文/自定义协议帧。

| 项 | 内容 |

## 四、测试 2：自定义协议帧
